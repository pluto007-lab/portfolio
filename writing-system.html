Development Case Study

Writing管理・分析システム

記事を掲載する作業だけでなく、更新・分析・履歴保存までを一つの運用フローとして設計した、自分用のローカル管理ツールです。

  1. 課題発見
  2. 要件整理
  3. 方式選定
  4. 実装
  5. 実運用
  6. データ蓄積

01 / Background

手入力が増える運用を、仕組みから見直す

note記事をポートフォリオへ掲載するたびに、タイトル、公開日、画像、紹介文を手入力していました。記事数が増えるほど、代表記事や掲載順を含めた更新作業も煩雑になります。

アクセス状況の分析にも、noteの画面からPV・スキ・コメントを確認し、手作業で記録する必要がありました。そこで、記事管理からアクセスデータの蓄積までを一つの仕組みにまとめました。

02 / Operation Flow

二つの流れを、一つの管理画面へ

記事を掲載する

  1. note URL入力
  2. 記事情報自動取得
  3. 管理画面で編集
  4. JSON書き出し
  5. Writingページへ反映

アクセス状況を蓄積する

  1. noteアクセス状況取得
  2. 既存記事と照合
  3. PV・スキ・コメント更新
  4. スキ率自動計算
  5. 取得時点のデータを履歴保存

03 / Features

運用に必要な機能

  • note URLから記事情報取得
  • 記事管理画面
  • カテゴリ・代表記事・掲載順管理
  • JSON / fallback書き出し
  • noteアクセス状況の半自動取得
  • 記事ID → URL → タイトルによる照合
  • 更新前後の差分確認
  • PV / スキ / コメント管理
  • スキ率自動計算
  • PV / スキ / スキ率などの並べ替え
  • アクセス状況snapshotの時系列保存

04 / Design Decision

完全自動化より、安全に確認できる半自動化

noteには一般ユーザー向けの公式APIがないため、ログインCookieやパスワードを外部へ保存する完全自動化は避けました。内部APIも使用せず、ログイン済みブラウザに表示されたDOMから必要な情報だけを取得します。

  1. 照合
  2. 差分確認
  3. ユーザー操作で反映

05 / Data Design

現在値と時系列履歴を分ける

Current

data/writing-articles.json

公開ページで使う最新の記事情報と現在値

History

data/writing-stats-history.json

取得日時ごとのPV・スキ・コメント

公開用データを肥大化させず、PV推移、スキ率推移、初動型・後伸び型、投稿後の既存記事への流入を後から分析できる構造にしています。

06 / Interface

画面で確認できること

画像を選択すると原寸で確認できます。時系列履歴は、データ蓄積後に同じ画像ファイルを更新します。
